# **Часть 1. Product Specification v1.0**
## **1.1. Описание проекта**
Luxury Store — цифровой каталог премиального мужского бутика. Проект не является интернет-магазином в классическом понимании. Это представительская платформа, которая решает четыре задачи: представление бренда в интернете, демонстрация ассортимента, показ готовых сочетаний товаров и предоставление сотрудникам бутика инструмента управления контентом.

Целевая аудитория сайта — мужчины 25–55 лет с высоким доходом: предприниматели, руководители, клиенты, покупающие костюмы и аксессуары премиум-класса. Средний чек начинается от 11 000 сомони. Это значит, что продукт продаёт не просто одежду, а статус, образ и уверенность.

Сайт должен ощущаться как цифровое продолжение дорогого бутика, а не как маркетплейс. При входе клиент не должен чувствовать ассоциаций с Wildberries, Ozon или AliExpress. Визуальная задача — листание каталога премиального бренда.
## **1.2. Что НЕ входит в MVP**
Следующие функции явно исключены из первой версии и проектируются только после её завершения:

- Корзина.
- Оформление заказа.
- Онлайн-оплата.
- Избранное.
- Личный кабинет клиента.
- История заказов.
- Программа лояльности.
- AI-рекомендации и алгоритмическое сочетание товаров.
- Чат с клиентом.
- Уведомления.
- Интеграции с CRM.
- Аналитика продаж.
## **1.3. Роли пользователей**
### **Гость (неавторизованный посетитель сайта)**
Доступные действия:

- Просмотр главной страницы.
- Просмотр каталога с фильтрацией и сортировкой.
- Открытие карточек товаров.
- Просмотр связанных товаров в карточке.
- Просмотр списка брендов и информации о бренде.
- Просмотр контактов и расположения бутика.
### **Администратор**
Доступные действия:

- Создание, редактирование и скрытие товаров.
- Управление брендами (создание, редактирование, удаление).
- Управление категориями.
- Загрузка и удаление изображений товаров.
- Создание связей между товарами (блок «Сочетается с этим»).
- Редактирование контента главной страницы.
## **1.4. Главная страница**
Главная страница состоит из шести блоков. Все блоки управляются администратором из админ-панели:

1. Hero-блок: крупное фоновое изображение или видео, заголовок, подзаголовок, кнопка перехода в каталог.
1. Баннер или видео коллекции.
1. Новые поступления — товары с флагом is\_new = true.
1. Популярные товары — товары с флагом is\_featured = true.
1. Блок о бренде — заголовок, описание, изображение.
1. Контактная информация — адрес, телефон, социальные сети, карта.
## **1.5. Каталог**
Раздел каталога поддерживает следующие возможности:

- Поиск по названию товара.
- Фильтр по бренду.
- Фильтр по категории.
- Фильтр по цвету.
- Фильтр по размеру.
- Сортировка: сначала новые, цена по возрастанию, цена по убыванию.
## **1.6. Карточка товара**
Каждая карточка товара содержит:

- Название.
- Бренд.
- Категорию.
- Описание.
- Состав ткани/материала.
- Цену в сомони и в долларах.
- Доступные размеры с указанием наличия.
- Галерею фотографий.
- Статус наличия.
- Блок «Сочетается с этим» со связанными товарами.
## **1.7. Связанные товары — ключевая функция**
Блок «Сочетается с этим» — главная коммерческая фишка проекта. Каждый товар может иметь произвольное количество связанных товаров. Например, к костюму администратор может вручную привязать обувь, ремень, рубашку и часы.

Принципиально важно: связи устанавливаются вручную администратором через админ-панель. Никакие автоматические рекомендации, алгоритмы или AI-механизмы в MVP не используются. Это сознательное решение по двум причинам: во-первых, это резко сокращает сложность разработки; во-вторых, владелец бутика лучше любого алгоритма знает, что с чем сочетается.

Бизнес-эффект функции — рост среднего чека: клиент видит не отдельную вещь, а готовый комплект, и покупает костюм + обувь + ремень + часы вместо одного костюма.
## **1.8. Бренды и категории**
**Для каждого бренда хранится:**

- Название.
- Логотип.
- Описание.

**Примеры категорий проекта:**

- Костюмы.
- Пиджаки.
- Брюки.
- Обувь.
- Ремни.
- Часы.
- Аксессуары.
## **1.9. Критерий успеха MVP**
Проект считается успешным, если выполнены два условия одновременно. Первое: клиент бутика, открывая сайт, ощущает дорогую визуальную подачу — премиальный сайт-каталог, а не шаблонный интернет-магазин. Второе: владелец бутика может полностью управлять каталогом, брендами, категориями, изображениями, связями товаров и контентом главной страницы без участия разработчиков.

# **Часть 3. API Contract v1.0**
## **3.1. Общие соглашения**
API реализован на Next.js API Routes. Все ответы имеют единый формат, описанный ниже. Авторизация требуется только для административных маршрутов. Frontend-разработчик не имеет права самостоятельно изменять структуру ответов API — за это отвечает backend.
### **Формат успешного ответа**
{ "success": true, "data": { ... } }
### **Формат ответа с ошибкой**
{ "success": false, "message": "Текст ошибки" }
### **Обработка ошибок**
Каждый endpoint обязан: проверять входные данные, возвращать понятную ошибку с осмысленным сообщением, не отдавать stack trace клиенту. HTTP-коды используются по назначению: 200 для успеха, 400 для валидационных ошибок, 401 для отсутствия авторизации, 404 для отсутствующих ресурсов, 500 для серверных ошибок.
## **3.2. Публичные endpoints**
### **GET /api/products**
Возвращает список товаров. Поддерживает query-параметры:

- search — поисковая строка.
- brand — фильтр по slug или id бренда.
- category — фильтр по slug или id категории.
- color — фильтр по цвету.
- size — фильтр по размеру.
- sort — сортировка (new, price\_asc, price\_desc).
### **GET /api/products/:slug**
Возвращает карточку конкретного товара. В data включаются: данные товара, изображения, размеры, бренд, категория, связанные товары.
### **GET /api/brands**
Возвращает список всех брендов.
### **GET /api/categories**
Возвращает список всех категорий.
### **GET /api/homepage**
Возвращает контент всех блоков главной страницы.
## **3.3. Административные endpoints**
Все маршруты требуют авторизации с ролью ADMIN.
### **Управление товарами**
- POST /api/admin/products — создание товара.
- PATCH /api/admin/products/:id — обновление товара.
- DELETE /api/admin/products/:id — скрытие товара (soft delete через is\_active).
### **Управление изображениями**
- POST /api/admin/product-images — добавление изображения.
- DELETE /api/admin/product-images/:id — удаление изображения.
### **Управление связями товаров**
- POST /api/admin/product-relations — создание связи.
- DELETE /api/admin/product-relations/:id — удаление связи.
### **Управление брендами**
- POST /api/admin/brands — создание бренда.
- PATCH /api/admin/brands/:id — обновление бренда.
- DELETE /api/admin/brands/:id — удаление бренда.
### **Управление категориями**
- POST /api/admin/categories — создание категории.
- PATCH /api/admin/categories/:id — обновление категории.
- DELETE /api/admin/categories/:id — удаление категории.
### **Управление главной страницей**
- PATCH /api/admin/homepage — обновление блоков главной страницы.
## **3.4. Авторизация**
В системе используется одна роль — ADMIN. Доступ к административным маршрутам разрешён только авторизованным пользователям этой роли. Авторизация реализуется через NextAuth или через собственную минималистичную admin-auth систему (на усмотрение backend-разработчика). Регистрация публичных пользователей в MVP не предусмотрена.
# **Часть 4. Frontend Screens Specification v1.0**
## **4.1. Общие принципы**
Сайт должен выглядеть как премиальный бутик, а не маркетплейс. Это требование к визуальной подаче, а не функционал. Базовые принципы оформления:

- Много свободного пространства, воздух между блоками.
- Крупные качественные изображения.
- Минимальное количество текста.
- Акцент на фотографиях товаров.
- Акцент на бренде и качестве.
- Отсутствие визуального шума, баннеров, кричащих CTA, скидочных лент.

Примечание: данный документ описывает структуру и наполнение экранов. Дизайн-направление (типографика, цветовая палитра, мудборд, референсы) фиксируется отдельным артефактом, который готовится фронтендером совместно с заказчиком до начала вёрстки.

# **Часть 6. Регламент работы с GitHub для команды из двух человек**
## **6.1. Базовая идея**
Для команды из двух разработчиков сложные Git-flow схемы создают больше проблем, чем решают. Используется максимально простая модель: один репозиторий, две постоянные ветки (main и develop), короткие feature-ветки, частые мерджи.
## **6.2. Распределение зон работы**
Главное правило — два разработчика не работают в одних и тех же файлах. Это снимает 90% возможных конфликтов.

**Backend работает в:**

- src/app/api/\*
- src/lib/db/\*
- src/lib/auth/\*
- prisma/\*

**Frontend работает в:**

- src/components/\*
- src/features/\*
- src/app/(public)/\*
## **6.3. Первый запуск проекта**
Один из разработчиков (обычно backend) создаёт репозиторий локально:

git init

git add .

git commit -m "init"

git branch -M main

git remote add origin REPO\_URL

git push -u origin main

Создаёт ветку develop:

git checkout -b develop

git push -u origin develop

Напарник клонирует репозиторий и переключается на develop:

git clone REPO\_URL

git checkout develop
## **6.4. Как брать задачу в работу**
Перед началом любой задачи:

git checkout develop

git pull origin develop

Только после этого создаётся feature branch:

git checkout -b feature/product-api

Если пропустить этап pull, через несколько дней появятся конфликты, которых можно было избежать.
## **6.5. Работа внутри ветки**
Коммит делается часто — минимум каждые 30–60 минут, а не раз в день и не раз в неделю. Пример:

git add .

git commit -m "feat: create product service"

git add .

git commit -m "feat: add product validation"
## **6.6. Завершение задачи**
Запушить ветку:

git push origin feature/product-api

На GitHub создать Pull Request: feature/product-api → develop. Напарник проверяет изменения. Если всё корректно — Merge Pull Request. После мерджа ветка удаляется. Каждая новая задача начинается с новой ветки.
## **6.7. Разрешение конфликтов**
Если оба разработчика изменили один и тот же файл, при мердже Git сообщит о конфликте. Действия: один из разработчиков открывает файл и вручную выбирает правильный вариант или объединяет изменения. Для команды из двух человек это занимает несколько минут.
## **6.8. Правило миграций Prisma**
Дополнительное правило для предотвращения конфликтов схемы БД: миграции Prisma делает только backend-разработчик. Frontend перед запуском проекта у себя локально обязательно подтягивает свежий develop и применяет миграции командой prisma migrate dev. Параллельные миграции в двух ветках запрещены.
## **6.9. GitHub Projects**
Рекомендуется завести доску GitHub Projects со следующими колонками:

- Backlog — необработанные задачи.
- Todo — задачи к выполнению.
- In Progress — в работе.
- Review — на проверке (Pull Request).
- Done — завершено.

Примеры карточек: Create Product API, Create Product Table, Create Catalog Filters, Create Brand CRUD, Create Homepage CMS. Доска даёт двум разработчикам общую видимость: что делать, кто делает, что готово.
## **6.10. Работа с Claude Code**
Каждая задача — отдельный чат Claude. Не смешивать задачи в одном чате, иначе контекст «плывёт» и качество кода падает. Примеры разделения:

- Чат 1 — Product API.
- Чат 2 — Admin Products Page.
- Чат 3 — Brand Management.
## **6.11. Рекомендуемый ритм работы**
Ежедневный созвон на 5 минут: выбрали задачи, создали ветки, разошлись работать. Вечером — мердж в develop.

Размер задачи — максимум 2–4 часа. Чем чаще изменения попадают в develop, тем меньше боли через месяц разработки. Никогда не накапливать неделю работы в одной ветке без мерджа — это самая распространённая причина проблем в маленьких командах.
